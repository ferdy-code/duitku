## 2026-10-12 — T-004 — repository conventions
- `user_id` is a mandatory positional parameter of every repository function and part of every WHERE (reads, updates, deletes). Not found and not yours look identical (`None` / `False` / empty), so no id can be used to probe another user's data. It is the second line of defence behind "`user_id` comes only from `RunnableConfig`": even a tool that forgets a filter cannot compile without a `user_id`.
- Foreign keys point at `categories.id` / `receipts.id` only, so Postgres would happily attach user B's category to user A's expense. Repos therefore check ownership before inserting/updating/upserting (`require_category`, `require_receipt`) and raise `domain.errors.NotOwnedError`. Tools (T-104) will map it to an observation.
- Repos take an `AsyncSession` and never commit: the caller owns the transaction. This is what makes "seed default categories in the same transaction as user creation" true (`get_or_create_user` -> `seed_defaults`; a test rolls back and finds neither). Seeding is `ON CONFLICT DO NOTHING`, so it is idempotent.
- `get_or_create_user` uses `INSERT .. ON CONFLICT DO NOTHING RETURNING`, then a SELECT on conflict: concurrent first messages cannot raise or double-seed. Returns `(user, created)`.
- Idempotency: `insert_expense` uses `INSERT .. ON CONFLICT (user_id, idempotency_key) WHERE idempotency_key IS NOT NULL DO NOTHING RETURNING`; no row back -> SELECT the existing one. Chosen over catch-IntegrityError because a failed statement aborts the surrounding Postgres transaction. Returns `InsertResult(expense, created)`. A replay ignores the new arguments (first write wins); NULL keys never collide.
- Updates/deletes use `UPDATE/DELETE .. RETURNING id` instead of `rowcount` (typed, and the result doubles as the "was it yours" signal). Expense deletes are soft (`deleted_at`) and deleted rows are invisible to every expense read. `update_expense` accepts only a whitelisted set of columns (never `user_id`, `idempotency_key`, `source`).
- Upserts that RETURN an ORM entity use `populate_existing` (otherwise the identity map hands back the stale pre-update object).
- `repositories/memories.py` is plain CRUD plus the vector column; embedding, dedupe, similarity recall and `recall_count` bookkeeping are T-302. `list_expenses` is a simple filtered list for tests/tools plumbing, not the aggregation path (`query_expenses`, T-104).
- Default category list lives in `domain/categories.py` (pure data), names from `data-model.md`.
- Doc note: `architecture.md` lists `repositories/{expenses,budgets,memories,users,audit}.py`; `categories.py` and `receipts.py` were added since those tables have their own ownership rules. `audit.py` covers both `agent_runs` and `tool_audit_log` (append-only, no update/delete).

## 2026-10-12 — migration 0002 — composite FKs against cross-user references
- Problem (flagged in T-004): `expenses.category_id`, `expenses.receipt_id`, `budgets.category_id` pointed at `categories.id` / `receipts.id` only, so Postgres accepted user A referencing user B's rows; only the repo ownership checks prevented it.
- Fix: `UNIQUE (user_id, id)` on `categories` and `receipts` (FK target; redundant with the PK for uniqueness but required by Postgres), and the three single-column FKs replaced by `(user_id, category_id) -> categories(user_id, id)` and `(user_id, receipt_id) -> receipts(user_id, id)`. The same-user rule is now enforced by the database for raw SQL, bugs and future tools, not just by `require_category` / `require_receipt`, which stay as defence in depth (they give a clean `NotOwnedError` instead of an `IntegrityError`).
- The originals had no `ON DELETE` action (NO ACTION), so none is added: no `SET NULL (col)` column-list form is needed. `receipts.id` deletion while referenced is still refused. Default MATCH SIMPLE keeps `receipt_id NULL` valid (`user_id` is NOT NULL, so only `receipt_id` can opt out of the check). Deleting a user still cascades (all rows go in one statement; NO ACTION is checked at statement end).
- Cost: one extra unique index per target table. Downgrade restores the exact 0001 constraints and names. Models mirror it with `ForeignKeyConstraint`; `compare_metadata` stays empty. `data-model.md` DDL updated to the final state.
- Apply to dev DB manually: `uv run alembic upgrade head` (not run by the agent).

## 2026-10-12 — T-101 — parse_idr_amount
- API: `parse_idr_amount(text) -> int`, raises `AmountError(code, message, hint)`. tools.md says both `-> int` and "error with a hint", so we raise: `domain` stays independent of the tool envelope, and the tool layer maps the exception to `{"ok": false, ...}`.
- Two codes: `AMBIGUOUS_AMOUNT` (could mean two amounts: `1.5`, `5m`, mixed separators, fractional rupiah) and `INVALID_AMOUNT` (zero, negative, > 10 billion, empty, no digits). `INVALID_AMOUNT` is new; the spec had no code for these. The agent asks the user to confirm in both cases, never guesses.
- No floats: `Decimal`/`int` only. With a multiplier (`rb`, `k`, `juta`, `jt`) `.` and `,` are decimal separators (`1,5 juta` = 1,500,000). Without one, only groups of exactly 3 digits with one repeated separator count as thousands (`35.000`).
- Footgun: `1.500rb` reads as 1,500 (follows the spec). Mention it in the tool description or prompt.

## 2026-10-12 — T-102 — resolve_period
- `resolve_period(period, now, tz) -> Period(start_date, end_date, label)`. `now` is injected, so the logic never reads the clock and tests are deterministic. Unknown period raises `InvalidPeriodError` (with `.hint`); T-104 maps it to `INVALID_ARGUMENT`.
- `end_date` is inclusive, matching `query_expenses` in tools.md, so output feeds the query without ±1 conversion.
- `this_week`/`this_month`/`this_year` end at today ("so far"), so future-dated expenses in the current period are excluded. Switching to full calendar periods is a small change if needed.
- `last_7_days`/`last_30_days` include today. Weeks start on Monday. Labels are Indonesian (user-facing).
- tools.md gap: it does not state these choices or an error code for an unknown period. Add them to the spec.

## 2026-10-12 — T-103 — tool envelope and audit decorator
- `tools/base.py`: `ok`/`error` envelope, `get_context(config)` (user_id and timezone only from `config["configurable"]`), `audited(tool_name)` decorator writing `tool_audit_log`.
- Mapping: `ValidationError`/`ValueError` -> `INVALID_ARGUMENT` with hint; any other exception -> generic `INTERNAL_ERROR` with no exception text (only the exception type is logged; traceback only when `LOG_CONTENT=true`). Audit args are redacted unless `LOG_CONTENT=true`. A failed audit write is logged and does not change the tool result.
- Deviation from tools.md: LangChain validates args against `args_schema` BEFORE our wrapper runs, so the decorator never sees those errors. T-104 tools must be built with `StructuredTool.from_function(coroutine=audited("x")(fn), name=..., handle_validation_error=validation_error_envelope)`; the `@tool` decorator does not accept that kwarg in the pinned langchain-core 1.6.9.
- Tool results are dicts that LangChain JSON-dumps into `ToolMessage.content`, so `data` must be JSON-serializable (no `date`/`UUID`).
- Open: `tool_audit_log` has no `tool_call_id` column; the id is only logged on audit failure. OTel span from tools.md skipped until the observability task. Broad `ValueError` mapping may leak library error text to the LLM; introduce an explicit `ToolError` if it bites.

## 2026-10-12 — T-104 — core tools (add_expense, query_expenses, resolve_period)
- Built as `StructuredTool`s via `build_*_tool(sessionmaker=None)`; the sessionmaker is resolved at call time, so tests inject the test DB and importing tools needs no settings. `tools/clock.py` is the only place that reads the time; tests override `clock.now`.
- Idempotency: `idempotency_key` = the injected `tool_call_id` (hidden from the LLM schema). A replay returns the stored row with `duplicate: true` (first write wins, even if the replay has a different category).
- `add_expense.amount` is `str` (parsed by `parse_idr_amount`); a validator also accepts an int because models often send numbers, while the schema stays `string`.
- Dates: `occurred_on` is a local date; stored `occurred_at` = that date + current time of day in the user's tz. Range queries use local-midnight bounds `[start, end+1 day)`; day/week/month buckets use `timezone(tz, occurred_at)` then `date_trunc` (Postgres weeks start Monday).
- `query_expenses` output: `total_idr`/`count` cover the whole range; `limit` only trims `rows` (flag `rows_truncated`); `groups` is never capped so sums equal the total; `rows` only when `group_by=none`. All numbers computed in SQL. Verified against a plain-Python reference over a 5 group_by x 5 ranges x 3 category filters x 2 timezones matrix, plus other-user and soft-deleted rows.
- New error codes (spec only named `INVALID_ARGUMENT`): `UNKNOWN_CATEGORY` (hint lists valid slugs), `NOT_FOUND` (foreign receipt), `CONFLICT` (IntegrityError), `INVALID_AMOUNT`/`AMBIGUOUS_AMOUNT` from the parser.
- Approval for `source="receipt"` lives in the graph `approval` node (later), not in the tool.
- tools.md gaps: no code for unknown category/foreign receipt/unknown period; future `occurred_on` allowed; `receipt_id` not enforced for `source="receipt"`; `groups[]` shape undefined (we return `{key, total_idr, count, name?}`, no avg).
- Risks: `group_by=day` over a year gives ~366 groups in LLM context; no guard against a wrong-year `occurred_on`; "this_*" periods hide future-dated rows (T-102). Check provider handling of nullable `anyOf` schemas in T-105/T-207.

## 2026-10-12 — T-105 — manual tool-calling loop (experiments/01_manual_loop.py)
- Goal: tool calling from first principles with the `openai` SDK only (Chat Completions; base_url/key/model from config), reusing the T-104 tools. No LangGraph.
- Message format: a plain list of dicts, re-sent in full on every call (the API is stateless). Roles: `system` (once, first; date + tz + "reply in Indonesian, never compute numbers"), `user`, `assistant`, `tool`. The conversation state IS this list; it was kept across both scenario turns, so turn 2 saw turn 1.
- The assistant message that requests tools: `{"role":"assistant","content":null,"tool_calls":[{"id","type":"function","function":{"name","arguments"}}]}`. `arguments` is a JSON STRING (the model can send invalid JSON), not a dict. It must be appended to `messages` before the results, WITH its tool_calls; otherwise the tool messages are orphans. `content` was null when tools were requested.
- Pairing: each `tool_calls[i].id` needs exactly one `{"role":"tool","tool_call_id":<same id>,"content":<str>}` message right after the assistant message. `content` is a string (our JSON envelope). A model can issue several calls in one message; each gets its own tool message. We always answer every id: unknown tool, bad/non-object JSON args and tool crashes become error envelopes (UNKNOWN_TOOL, INVALID_ARGUMENT, INTERNAL_ERROR; no exception text), tested with a fake client. OpenAI's own API rejects a missing answer with HTTP 400 ("An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'") — from knowledge, not observed here. OBSERVED: our configured gateway did NOT reject an unanswered tool_call (it returned finish_reason=stop). Do not rely on that leniency; the invariant stays mandatory.
- Stop condition: loop until the response has no `tool_calls` (finish_reason "stop" instead of "tool_calls"). We key on the presence of tool_calls: if present we must answer them anyway (some gateways report a wrong finish_reason); if finish_reason says tool_calls but none are present there is nothing to run. Guard: at most `max_agent_steps` model calls per user turn, checked only after all tool calls of a step were answered, so history stays valid. On cap we return a fixed message.
- Schema: `tool.tool_call_schema.model_json_schema()` is the LLM-facing schema (injected `config`/`tool_call_id` stripped). `get_input_jsonschema()` leaks `tool_call_id`; do not use it. Tools run via `ainvoke({"name","args","id","type":"tool_call"}, config=...)`; passing a ToolCall (not bare args) is what makes InjectedToolCallId, and therefore the idempotency key, work.
- Provider check (answers the T-104 risk): the gateway accepted our nullable `anyOf` + `null` defaults schema unchanged (no flattening needed). The model sent only the args it needed, passed the amount as the raw string "35rb", and picked the category slug correctly.
- Observed: "total hari ini" chained 2 tools (resolve_period -> query_expenses) as the descriptions intend, 3 LLM calls in that turn. Tokens per call grow with history: 1950 -> 2580 (system prompt + 3 tool schemas are most of the ~1.9k baseline). The reply was Indonesian and quoted `total_idr` verbatim, no own arithmetic. DB check: exactly one expense of 35000; 3 `tool_audit_log` rows.
- Learning: this ~100-line loop is the whole ReAct agent. LangGraph (Phase 2) adds persistence/checkpoints, `interrupt()` for approval, and step/recursion limits, not new tool-calling mechanics.
- Notes: the script uses a fixed dev-DB experiment user (telegram id 900000105); `--reset` deletes it and its rows by cascade. `[tool.pyright] include` now covers `experiments`.

## 2026-10-12 — T-204 — history trimming
- `trim_history(messages, max_tokens)` returns a new list (input never mutated) using langchain-core `trim_messages(strategy="last", start_on="human", token_counter="approximate")`. A window that starts on a HumanMessage can never start with an orphan ToolMessage or split a tool_calls/ToolMessage group, so no custom group logic is needed.
- Floor: the window is never smaller than `messages[last_human:]` (trim_messages returns [] when the last turn alone exceeds the budget), so the mandatory part may exceed the budget. No human message -> list unchanged. The caller prepends the system prompt; `max_tokens` is a parameter.
- Shortcut: the approximate counter is ~chars/4; swap for a real tokenizer if accuracy matters.
- agent.md gap: it wants recent `add_expense`/`query_expenses` ToolMessages kept so "the last one" works (R-05) but gives no mechanism; they survive only if inside the budget.

## 2026-10-12 — T-206 — update_expense and get_exchange_rate
- `update_expense` takes an explicit `expense_id`; there is no "last" shortcut (tools.md has none, and a tool that guesses which row to edit can silently change the wrong one). The agent gets the id from the `add_expense` result or from the first row of `query_expenses` (group_by=none, newest first). R-05 test: 3 expenses for A, a newer one for B, a newest soft-deleted one for A -> "the last one" resolves to A's third and only that row changes.
- Partial update (at least one field); `merchant`/`note` = "" clears; `occurred_on` keeps the original time of day. Returns `{expense_id, old, new}`. Missing, foreign, and soft-deleted ids give identical `NOT_FOUND`. "Last" means newest by `occurred_at`, so a backdated entry added later is not "last" — decide in the system prompt whether last should mean last added.
- `get_exchange_rate` uses Frankfurter (`https://api.frankfurter.dev/v1/latest?base=X&symbols=Y`). JSON parsed with `parse_float=Decimal`; IDR results `converted_idr` is an int (half-up once). One immediate retry on timeout/network/5xx, none on 4xx; 404/422 -> `UNKNOWN_CURRENCY`, everything else -> `UPSTREAM_ERROR`. Per-instance cache keyed (from, to), 1h TTL via `clock.now()`, failures not cached. Timeout is `TOOL_TIMEOUT_SECONDS` (tools.md says 5s; the setting defaults to 10). Same currency both sides -> rate 1, no HTTP.
- Shortcut: retry has no backoff.
- Process lesson: parallel workers must not run integration tests at the same time; they share one `<db>_test` that every test drops and recreates. From now on only one worker per wave runs integration tests.

## 2026-10-12 — T-202 — graph v1 (agent <-> tools)
- Step cap is a routing counter, not langgraph's recursion limit. Model calls this turn = number of AIMessages since the last HumanMessage (derived from history, no extra state field). `route_after_agent`: no tool_calls -> END; tool_calls and count < `MAX_AGENT_STEPS` -> `tools`; tool_calls and count >= max -> `limit` node. Why: `GraphRecursionError` fires between supersteps and can leave an AIMessage with unanswered tool_calls in the stored thread, which poisons it (the API then returns 400).
- The `limit` node answers every pending id with an error ToolMessage (`STEP_LIMIT`, not executed), then appends an Indonesian fallback AIMessage. So the model gets at most MAX_AGENT_STEPS calls and the capped step's tools are refused: running side-effecting tools whose result can never be reported to the user seemed worse. Downside: earlier steps in the same turn may already have saved something, and the neutral fallback does not say what.
- Backstop: `run_turn` sets `recursion_limit = 2*max+5` (the counter always fires first) and catches `GraphRecursionError` into a fallback reply. That path should be unreachable and can leave a dangling AIMessage in the thread; repair with `aupdate_state` if it ever shows up. `run_turn` builds the full `AgentState` input each turn, which resets `rejected_call_ids`. `with_config` is not used for the limit because it turns the compiled graph into a `RunnableBinding` that loses `aget_state`.
- Custom tools node instead of prebuilt `ToolNode`: one ToolMessage per tool_call_id guaranteed. Unknown tool -> `UNKNOWN_TOOL`; raising tool -> `INTERNAL_ERROR` (no exception text); unparseable args (`invalid_tool_calls`, which langchain-openai re-sends to the API) -> `INVALID_ARGUMENT`; a call with no id is skipped. Tools get the whole ToolCall dict (so `InjectedToolCallId` / the idempotency key work) and run sequentially (deterministic order; calls may depend on each other).
- Agent node: model view = system prompt + `trim_history(...)`; stored state untouched and holds no SystemMessage. Category slugs come from the repo for the config's user_id, falling back to `DEFAULT_CATEGORIES` on any failure (only the exception type is logged). `ChatOpenAI` is built from settings with `max_retries=1`. `user_id`/`timezone` only from `config["configurable"]` (test: LLM-supplied values are ignored).
- Prompt: rule 11 added ("to change/delete 'the last one', take expense_id from the add_expense result or the first row of query_expenses group_by=none; never guess"). Prompt change -> rerun evals in T-207. It does not settle "last = newest by occurred_at" vs "last added".
- pyright: one `reportMissingTypeStubs = "none"` in pyproject (langgraph is a namespace package); inline ignores removed. `graph.py` has a file-level `reportUnknownMemberType=false` because langgraph's own signatures contain `Command[Unknown]`.
- agent.md gap: "cap steps via recursion_limit ≈ 2*MAX+1" is unreliable (see above); it should describe the routing counter plus `limit` node, with recursion_limit only as backstop. Each agent step runs one small category query (no per-turn cache).

## 2026-10-12 — T-205 — runner and CLI
- `TurnRunner(graph, sessionmaker=None)` in `interfaces/runner.py` is interface-agnostic (Telegram reuses it). `resolve_user` -> `get_or_create_user` (seeds categories); a new user gets `DEFAULT_TIMEZONE` (the column default is hard-coded 'Asia/Jakarta', so changing the env later does not update existing users). `run(thread_id, UserCtx, message)` builds `configurable = {user_id, timezone, thread_id}` from the user row, takes a per-thread lock, calls `agent.graph.run_turn`, returns `TurnResult(text, trace, failed)`. Any turn exception -> Indonesian `ERROR_REPLY`, `failed=True`; only the exception type is logged (traceback only if `LOG_CONTENT=true`). The `except Exception` there is deliberate: the interface must not crash.
- Locks: `WeakValueDictionary[str, asyncio.Lock]`, so the dict does not grow with every thread ever seen. Per-process only; multiple workers would need a Postgres advisory lock. Concurrency test: 3 turns on one thread run one at a time (peak 1), two different threads overlap (peak 2). No mutation check that the test fails without the lock.

## 2026-10-13 — T-302 — memory store
- `memory/store.py`: `save` (embed_passage -> nearest same-user, same-kind memory -> UPDATE if similarity >= `dedupe_threshold`, else INSERT), `recall` (embed_query -> top_k with similarity >= `min_similarity`, ordered by similarity), `forget(memory_id)`. Similarity = 1 - pgvector cosine distance (`<=>`). Thresholds are parameters; `memory/thresholds.py` reads `MEMORY_*_THRESHOLD` from settings and raises `ConfigError` while they are None (T-303 sets them); no default numbers in code.
- Dedupe is SAME-KIND only (memory.md is silent): an update keeps the row's kind, so cross-kind dedupe would let a goal overwrite a preference row. Cost: the same sentence saved under two kinds gives two rows.
- Order is validate -> embed -> DB, so an `EmbeddingError` leaves no partial write. The store also checks `len(vec) == EMBEDDING_DIM` and raises `EmbeddingError` before the statement, so the transaction is not aborted. Over-long content (> 300 chars, matching the prompt's rendering cap from T-201) is rejected, not truncated: truncation would silently corrupt a fact, and the rejection lets the LLM rewrite it. `InvalidMemoryError` is a `ValueError` (the tool layer maps it to `INVALID_ARGUMENT`). `validate_content` is the single hook T-304 extends with the sensitive-data regex.
- `recall` does its bookkeeping (`recall_count + 1`, `last_recalled_at = now()`) in the same call and the caller's transaction, for returned memories only, and returns plain dataclasses (no stale ORM rows). So the count mixes automatic and explicit recalls. Empty query or `top_k < 1` returns `[]` without embedding.
- Repository: `nearest_memories` and `mark_recalled` added; `user_id` is in every WHERE; `update_memory` uses `populate_existing`. No `forget_by_query` (tools.md only defines `forget_memory(memory_id)`); the agent finds ids through `recall`.
- Tests use `tests/fake_embedder.py` (strings -> controllable unit vectors with exact cosines). EXPLAIN with seqscan off shows `memories_embedding_idx`; that proves the index is usable, not that the planner picks it by default.
- Risks: (1) HNSW with `user_id` as a post-filter can miss a user's nearest neighbour when there are many users; harmless at personal scale, else set `hnsw.iterative_scan = relaxed_order` (pgvector 0.8+) or partition by user. (2) A `dedupe_threshold` of exactly 1.0 can miss an identical vector through float rounding; T-303 must pick a value below 1.0. (3) Concurrent `save` calls of the same near-duplicate can both insert; the per-thread lock mostly covers it, a per-user advisory lock would close it. (4) Real E5 score distributions are untested here (T-303).

## 2026-10-13 — T-303 — memory threshold calibration (e5-small vs bge-m3)
- Experiment: `experiments/calibrate_memory_threshold.py [--models e5,bge]`; data in `experiments/calibration/pairs.py` (42 recall pairs, 25 dedupe pairs + 5 "supersede" pairs; deterministic stratified 50/50 dev/test); raw scores and tables in `experiments/results/memory_calibration.md` (committed as evidence). Indonesian pairs incl. slang/typos ("gofud", "kpn gajian"), hard negatives (transport query vs food memory, budget makan vs budget transport, chit-chat that must recall nothing).
- Label policy: recall "relevant" = a good assistant should inject this memory for this message. Dedupe `dup` = same fact in different words (merge); `distinct` = different merchant/category/item (never merge). Conflicting update ("budget makan 1,5 juta" vs "2 juta") = `supersede`: overwrite is the right outcome, but embeddings cannot tell a changed number from a paraphrase, so supersede pairs are NOT used to fit thresholds (reported separately).
- Results (CPU, WSL2): recall AUC e5 0.867 vs bge-m3 0.902; max recall at precision >= 0.9 is 0.68 for both. Dedupe AUC e5 0.654 vs bge 0.808; recall at P=1.0: e5 0.17, bge 0.50. e5: 384 dim, ~0.9 GB RSS, 33-40 ms/text, 0.47 GB disk. bge-m3: 1024 dim, ~2.8 GB RSS, 210-270 ms/text, 2.3 GB disk, needs a new migration + re-embed.

At 0.985 only 1 of 12 paraphrases merge: dedupe effectively collapses near-verbatim repeats only. Revisit bge-m3 only if dedupe misbehaves in real use or in T-306 (starting values ~0.53 recall, ~0.89 dedupe).
- Caveats: tiny hand-written dataset, indicative only; gaps of 0.003/0.001 are at the edge of noise; the dev-picked dedupe threshold failed on the test split (0.975 gave P 0.5). Minimal-pair negatives (one changed merchant or item) score 0.94-0.98 on e5, the same band as true paraphrases.
- Config: thresholds are now plain `float` settings with defaults 0.835/0.985 (`ge=0, lt=1`, env override wins, blank = default), calibrated values also in `.env.example` (not `.env`). `memory/thresholds.py` is two thin accessors (the "unset" `ConfigError` can no longer happen). Changing `EMBEDDING_MODEL` requires re-calibration. pytest `pythonpath`, pyright `extraPaths` and ruff `src` now include `experiments`.
- memory.md flaw: "cosine >= threshold -> overwrite" is too weak for safe auto-update on e5. It misses real updates (budget 1,5 -> 2 juta scores 0.973 < 0.985) and would merge Gojek with Grab if the threshold were lowered. Proposal for T-304: the agent reconciles updates itself (`recall_memory` first, then `forget_memory` + re-save, or save the updated text); the 0.985 store-level dedupe only collapses near-verbatim repeats.

## T-305: load_context node (auto-recall)

- Graph is now `START -> load_context -> agent -> ...`. - Layout: `interfaces/telegram/{bot,app,guards,handlers,formatting,texts}.py`. Updates without `effective_user`, and non-private chats, are dropped silently (threads are keyed by chat id, so a group would mix users; stricter than the spec). The guard logs a generic warning with no user id or content.
- Rate limit: in-memory sliding window of `RATE_LIMIT_MESSAGES_PER_MINUTE` per user; only accepted messages count, so spamming does not extend the block. Bounded by allowlist size. Resets on restart (acceptable for a single process).
- Updates are processed sequentially (PTB default), not with `concurrent_updates`: it keeps per-user message order ("eh salah, 15rb" must follow the previous message), at the cost that one slow LLM turn blocks all users. Revisit with more than a few users; `concurrent_updates` would also reorder because `resolve_user` runs before the per-thread lock.
- Replies: `html.escape(quote=False)` + `parse_mode=HTML`; split into <=4096 chunks BEFORE escaping so entities are never cut; one plain-text retry on `BadRequest`. Input cap 2000 chars (refused politely, agent not invoked). Typing indicator is re-sent every ~4 s while the runner works. Only `/start` and `/bantuan` are registered; `/batal` (T-403) and `/lupakan` come later; unknown commands and non-text messages are ignored.
- Startup: `warm_up_embedder()` first (T-305), then `open_checkpointer` via an `AsyncExitStack` closed in `post_shutdown`. httpx/httpcore loggers are set to WARNING so the bot token in request URLs is never logged. Non-config startup failures print the exception type only, never the message (it can embed the token/URL).
- For T-403: `allowed_updates` is `["message"]`; add `callback_query`, a `CallbackQueryHandler`, and a callback branch in the guard (it only rate-limits `update.message` now).
- Doc flaws: interfaces-ops.md says "middleware" (PTB has none) and does not define group-chat behaviour or the rate-limited reply; it names `run_turn(thread_id, user_ctx, message)` but the API is `TurnRunner.run`; "log with trace id" is impossible before T-406 (error handler logs the exception class only).

## T-405: `interrupt` idempotency

- Proof (tests/integration/test_approval_idempotency.py, 8 tests): `make_approval_node` is wrapped to count body runs and flag "in node"; a `before_cursor_execute` listener records every statement issued while the flag is set. Result: the node issues only SELECTs (the read-only, ownership-scoped `_human_summary` lookup); row counts of `tool_audit_log`, `expenses`, soft-deleted expenses, `memories`, `agent_runs` are identical before the turn, at the pause and after a reject; after approve the writes rise by exactly 1 per risky call and happen in `tools`, after the last answer. Mutation check: injecting an UPDATE into the lookup failed 4 tests.
- k risky calls in one AIMessage = k+1 node body runs and 2k+1 lookups, but exactly k effects (verified for k=1 and k=2, with a safe call in the same message waiting until all answers are in).
- Second resume: at the runner, further approve/reject returns the nothing-pending reply; on the raw graph in langgraph 1.2.14, `Command(resume=...)` on a thread that already reached END is a no-op (returns stored state, no node, no model call, no write). So the runner guard is defence in depth; it is needed for a NEVER-STARTED thread (resume would run from START on empty state; T-402 finding, not retested here). Earlier answers are replayed by position: a late approve cannot flip a recorded reject. Restart between every step (fresh Postgres checkpointer + graph before run, each resume and a late resume) still gives exactly one delete per risky call.
- Note: a test double wrapping the approval node must annotate `config: RunnableConfig`; with `Any`, langgraph does not inject config and the turn fails with a TypeError.
- Not verified: concurrent double-tap races (per-thread lock not stress-tested), `add_expense(source="receipt")` through this path (same node code, no test), `agent_runs` assertion is trivial until T-406.
